# 发布版本

直接创建并推送 `v*` 标签即可发布，无需手动运行脚本或填写更新日志。

`release.yml` 自动准备说明、运行测试、构建双架构安装包，然后创建对应标签的 GitHub Release。说明的来源按以下顺序选择：

1. `CHANGELOG.md` 中有与标签对应的非空版本节（例如 `[v0.3.11]`）时，使用人工整理的内容。
2. 没有对应节、内容为空或文件不存在时，自动根据上一个可达版本标签到此次标签之间的提交生成说明。首次发布使用该标签以前的全部提交；没有新增提交时明确标注。

如需人工整理，可将 `[Unreleased]` 内容移到待发布版本节，再保留空的 `[Unreleased]` 节供后续开发使用。这是可选步骤。自动生成不会将 `[Unreleased]` 中可能属于未来版本的内容混入此次说明。

CI 检出完整 Git 历史和标签。说明始终针对此次标签生成，发布期间 main 的新提交不会混入；重复版本节、非法标签和无法解析的 Git 历史仍会报错，避免发布错误内容。重新运行发布任务会更新同一版本的说明和附件。

本地预览也是可选的：创建标签后运行 `python3 scripts/release_notes.py --tag v0.3.11`。

`release-notes.md` 同时包含在安装包中并作为 Release 附件保留。安装包也包含完整的 `CHANGELOG.md`。Web 检查更新仍通过 GitHub 最新版跳转获取版本号；发现更新后，通过 GitHub API 按该标签读取 Release 正文。因此，在 Release 页面修订说明后，下次打开升级弹窗就能看到修订内容。未登录的 GitHub API 每个 IP 每小时只有少量额度，代理出口常被用尽（返回 403），这时改为下载该版本的 `release-notes.md` 附件，此时看不到发布后在页面上的修订。

历史版本没有说明时，Web 弹窗会明确提示该版本未提供发布说明。发布说明仅供参考：获取失败时，弹窗内显示错误并可重新获取，仍可直接确认升级。
